# 附錄 A：GBrain 架構說明

> 適用版本：v0.5.11。給第一次接觸 GBrain 的讀者：**為什麼 Operoid 需要一顆「腦」**，以及它與你聽過的「RAG」「Wiki 搜尋」有什麼不同。不想讀架構、只想操作——直接看[第 07 章](07-brains-and-models.md)即可，本附錄回頭再讀。

## 先從一個問題開始

問員工一個真實的公司問題：

> 「蝕刻製程去年是哪家供應商出過問題？後來怎麼收尾的？」

答案散落在你公司的文件裡：某場會議紀錄提到那次異常、供應商頁有這家公司的資料、專案頁有後續處理。**沒有任何一頁把這三件事寫在一起**——人類員工靠「翻資料＋串起來」回答；AI 員工要能做同樣的事，它需要一個能被翻、能被串的知識本體。這就是腦。

## 三條路：Wiki 搜尋、RAG、GBrain

### 路 1：Wiki 搜尋（關鍵字全文檢索）

你公司可能已經有 Notion／Confluence／內部 Wiki。直接拿關鍵字去搜，問題在哪？

- **只找得到「寫過的詞」**——搜「蝕刻 供應商」找不到一頁只寫「Etch chamber 異常」的會議紀錄；用詞稍微不同就錯過。
- **頁與頁之間沒有結構**——搜到十頁含「供應商」的文件，但系統不知道哪一家供應商、跟哪場會議有關。
- **跨頁問題無解**——「哪家供應商＋哪場會議＋怎麼收尾」需要把三頁串起來，關鍵字搜尋只會給你三個各自為政的結果。

### 路 2：一般單獨 RAG（chunk → embed → top-k）

RAG（Retrieval-Augmented Generation）把文件切碎、算向量、取最像的前 k 段塞給模型。這解決了「用詞不同」的問題——語義相近就能命中。但把 RAG 直接接給 AI 員工，還是缺三樣東西：

1. **只有碎片，沒有知識**——取回來的是一段段無名的文字。哪份文件、誰寫的、跟哪些實體有關，全都不知道；多跳推理（供應商→會議→結案）變成碰運氣。
2. **圖表通常直接消失**——切塊管線對圖片、表格無能為力；而工程知識恰恰大量活在圖裡。
3. **沒有治理**——傳統 RAG 沒有「誰在問」的概念。同一個問題，實習生和財務長取回同樣的東西——在組織裡這不是功能，是事故。

### 路 3：GBrain——結構化知識腦

GBrain 是 Operoid 使用的開源知識圖譜引擎（安裝與官方說明見 [github.com/garrytan/gbrain](https://github.com/garrytan/gbrain#cli-standalone-no-agent)）。它同時維護三個互相強化的層：

| 層 | 是什麼 | 怎麼來的 |
|---|---|---|
| **頁面（wiki）** | 人可讀、有型別的知識頁——人物、公司、會議、專案、概念……每頁有 YAML front matter（`type`／`title`／`tags`） | [文件工廠](09-factories.md)把 PDF／CSV／圖片轉成頁；你也可以手寫 |
| **圖譜（graph）** | 頁面之間的實體連結：誰任職於哪家公司、哪場會議提到哪個專案、哪張圖屬於哪份文件（`image_of`） | 寫頁時的 `[[wikilink]]` 自動成邊；LLM 富集會替你補連結 |
| **向量（embeddings）** | 每頁（與每張圖）的語義索引，本機模型（EmbeddingGemma 2）計算 | `sync` 時自動 embed |

查詢時三路融合：關鍵字與語義並用（`ask`／`query`）、沿圖譜跳（`think` 多跳合成）、需要時把圖表當獨立檢索項帶回。開頭那個問題的旅程變成：命中異常會議頁 → 圖譜帶出供應商實體 → 沿時間線找到結案報告——**三頁串成一句有出處的回答**。

### 三條路對照

| | Wiki 搜尋 | 單獨 RAG | **GBrain（Operoid 的腦）** |
|---|---|---|---|
| 資料形態 | 整頁文件 | 無名碎片 | 有型別的頁面＋實體圖譜 |
| 用詞不同找得到嗎 | ✗ | ✓ | ✓ |
| 跨頁多跳問題 | ✗ | 碰運氣 | ✓（`think` 沿圖譜合成） |
| 圖表可檢索 | ✗ | 通常 ✗ | ✓（圖表向量＋圖說；複雜 PDF 經 MinerU） |
| 知道「誰在問」 | ✗ | ✗ | ✓（檢索前授權，見下） |
| 人還能讀改嗎 | ✓ | ✗（碎片） | ✓（頁面就是 git repo 裡的 markdown） |
| 改一頁要重算全部嗎 | — | 通常要 | 不用——`sync` 增量 embed |

## 為什麼 Operoid 要「一顆腦」，而不是內建一個 RAG 模組

1. **執行與知識分離**。Operoid 的 Runtime 管理員工的執行——喚醒、恢復上下文、休眠；**從不管理思考**。知識是員工的推理素材，交給獨立的大腦：升級一顆腦，多個員工同步受益。
2. **知識必須有出身、有邊界**。員工答「公司的事」，每一句都該能溯源到具體頁面；每一次特權檢索都該留收據（誰、哪個任務、依哪版政策、看到哪些——見[第 13 章](13-governance.md)）。**同一顆腦、同一個查詢、不同身份 → 不同結果**；政策缺失＝拒絕（fail closed）。這些是架構，不是檢索器的附屬功能。
3. **頁面歸你所有**。知識以 markdown 頁面存在**你自己的** git repo 裡——人可以讀、可以改、可以回退版本；GBrain 只是在上面維護圖譜與向量。沒有黑箱資料庫把你鎖進去。

## 維護一顆健康的腦

- **sync 紀律**：寫入後同步（個人版工廠預設自動）；sync = commit + sync + embed + extract。
- **doctor**：健康檢查；**orphans** 找孤立頁（沒有任何入邊——代表它沒接進知識網路）。
- **schema**：新腦建議用 schema pack v2（15 標準型別）；v1 腦可「unify-types」遷移（[第 09 章](09-factories.md)）。
- **嵌入服務**：本機 llama-server 必須常駐（見[第 02 章](02-requirements.md)）——它不在，檢索退為僅關鍵字。
- **版本歷史**：頁面在 git 裡；agent 誤改可回退（`revert_version`）。

## 常見誤解

**「GBrain 就是一個向量資料庫？」** 不是。向量只是三層之一；圖譜與型別化頁面才是它回答跨頁問題、支撐治理的本錢。

**「我已經有 Notion／Confluence 了，還需要嗎？」** 那些是**儲存**；GBrain 是把儲存的內容**變成可推理的知識**——用詞不同的內容找得到、頁與頁連得起來、圖表搜得到。而且內容仍以 markdown／git 為本，不鎖平台。

**「RAG 就夠了吧？」** 個人玩具，或許。組織場景的三個硬需求——多跳推理、圖表檢索、檢索前授權——正是單獨 RAG 缺的三塊。

**「員工會把機密查出去嗎？」** 這正是「檢索前授權」在管的事：查詢先過政策（DENY→ALLOW→fail closed），越權的內容根本不會進入員工的上下文；每筆特權檢索留收據（[第 13 章](13-governance.md)）。

**「資料會上傳到哪裡？」** 腦資料是你機器上的檔案（PGLite＋git repo），嵌入走本機 llama-server。會離開機器的只有模型推論本身（你設定的 LLM 端點）——清單見 [DEPLOYMENT.md §11.4](../DEPLOYMENT.md)。
