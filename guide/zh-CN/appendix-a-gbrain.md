# 附录 A：GBrain 架构说明

> 适用版本：v0.5.11。给第一次接触 GBrain 的读者：**为什么 Operoid 需要一颗「脑」**，以及它与你们听过的「RAG」「Wiki 搜索」有什么不同。不想读架构、只想操作——直接看[第 07 章](07-brains-and-models.md)即可，本附录回头再读。

## 先从一个问题开始

问员工一个真实的公司问题：

> 「蚀刻制程去年是哪家供应商出过问题？后来怎么收尾的？」

答案散落在你公司的文件里：某场会议记录提到那次异常、供应商页有这家公司的资料、项目页有后续处理。**没有任何一页把这三件事写在一起**——人类员工靠「翻资料＋串起来」回答；AI 员工要能做同样的事，它需要一个能被翻、能被串的知识本体。这就是脑。

## 三条路：Wiki 搜索、RAG、GBrain

### 路 1：Wiki 搜索（关键字全文检索）

你公司可能已经有 Notion／Confluence／内部 Wiki。直接拿关键字去搜，问题在哪？

- **只找得到「写过的词」**——搜「蚀刻 供应商」找不到一页只写「Etch chamber 异常」的会议记录；用词稍微不同就错过。
- **页与页之间没有结构**——搜到十页含「供应商」的文件，但系统不知道哪一家供应商、跟哪场会议有关。
- **跨页问题无解**——「哪家供应商＋哪场会议＋怎么收尾」需要把三页串起来，关键字搜索只会给你三个各自为政的结果。

### 路 2：一般单独 RAG（chunk → embed → top-k）

RAG（Retrieval-Augmented Generation）把文件切碎、算向量、取最像的前 k 段塞给模型。这解决了「用词不同」的问题——语义相近就能命中。但把 RAG 直接接给 AI 员工，还是缺三样东西：

1. **只有碎片，没有知识**——取回来的是一段段无名的文字。哪份文件、谁写的、跟哪些实体有关，全都不知道；多跳推理（供应商→会议→结案）变成碰运气。
2. **图表通常直接消失**——切块管线对图片、表格无能为力；而工程知识恰恰大量活在图里。
3. **没有治理**——传统 RAG 没有「谁在问」的概念。同一个问题，实习生和财务总监取回同样的东西——在组织里这不是功能，是事故。

### 路 3：GBrain——结构化知识脑

GBrain 是 Operoid 使用的开源知识图谱引擎（安装与官方说明见 [github.com/garrytan/gbrain](https://github.com/garrytan/gbrain#cli-standalone-no-agent)）。它同时维护三个互相强化的层：

| 层 | 是什么 | 怎么来的 |
|---|---|---|
| **页面（wiki）** | 人可读、有类型的知识页——人物、公司、会议、项目、概念……每页有 YAML front matter（`type`／`title`／`tags`） | [文档工厂](09-factories.md)把 PDF／CSV／图片转成页；你也可以手写 |
| **图谱（graph）** | 页面之间的实体链接：谁任职于哪家公司、哪场会议提到哪个项目、哪张图属于哪份文件（`image_of`） | 写页时的 `[[wikilink]]` 自动成边；LLM 富集会替你补链接 |
| **向量（embeddings）** | 每页（与每张图）的语义索引，本地模型（EmbeddingGemma 2）计算 | `sync` 时自动 embed |

查询时三路融合：关键字与语义并用（`ask`／`query`）、沿图谱跳（`think` 多跳合成）、需要时把图表当独立检索项带回。开头那个问题的旅程变成：命中异常会议页 → 图谱带出供应商实体 → 沿时间线找到结案报告——**三页串成一句有出处的回答**。

### 三条路对照

| | Wiki 搜索 | 单独 RAG | **GBrain（Operoid 的脑）** |
|---|---|---|---|
| 数据形态 | 整页文件 | 无名碎片 | 有类型的页面＋实体图谱 |
| 用词不同找得到吗 | ✗ | ✓ | ✓ |
| 跨页多跳问题 | ✗ | 碰运气 | ✓（`think` 沿图谱合成） |
| 图表可检索 | ✗ | 通常 ✗ | ✓（图表向量＋图说；复杂 PDF 经 MinerU） |
| 知道「谁在问」 | ✗ | ✗ | ✓（检索前授权，见下） |
| 人还能读改吗 | ✓ | ✗（碎片） | ✓（页面就是 git repo 里的 markdown） |
| 改一页要重算全部吗 | — | 通常要 | 不用——`sync` 增量 embed |

## 为什么 Operoid 要「一颗脑」，而不是内置一个 RAG 模块

1. **执行与知识分离**。Operoid 的 Runtime 管理员工的执行——唤醒、恢复上下文、休眠；**从不管理思考**。知识是员工的推理素材，交给独立的大脑：升级一颗脑，多个员工同步受益。
2. **知识必须有出身、有边界**。员工答「公司的事」，每一句都该能溯源到具体页面；每一次特权检索都该留收据（谁、哪个任务、依哪版政策、看到哪些——见[第 13 章](13-governance.md)）。**同一颗脑、同一个查询、不同身份 → 不同结果**；政策缺失＝拒绝（fail closed）。这些是架构，不是检索器的附属功能。
3. **页面归你所有**。知识以 markdown 页面存在**你自己的** git repo 里——人可以读、可以改、可以回退版本；GBrain 只是在上面维护图谱与向量。没有黑箱数据库把你锁进去。

## 维护一颗健康的脑

- **sync 纪律**：写入后同步（个人版工厂默认自动）；sync = commit + sync + embed + extract。
- **doctor**：健康检查；**orphans** 找孤立页（没有任何入边——代表它没接进知识网络）。
- **schema**：新脑建议用 schema pack v2（15 标准类型）；v1 脑可「unify-types」迁移（[第 09 章](09-factories.md)）。
- **嵌入服务**：本地 llama-server 必须常驻（见[第 02 章](02-requirements.md)）——它不在，检索退为仅关键字。
- **版本历史**：页面在 git 里；agent 误改可回退（`revert_version`）。

## 常见误解

**「GBrain 就是一个向量数据库？」** 不是。向量只是三层之一；图谱与类型化页面才是它回答跨页问题、支撑治理的本钱。

**「我已经有 Notion／Confluence 了，还需要吗？」** 那些是**存储**；GBrain 是把存储的内容**变成可推理的知识**——用词不同的内容找得到、页与页连得起来、图表搜得到。而且内容仍以 markdown／git 为本，不锁平台。

**「RAG 就够了吧？」** 个人玩具，或许。组织场景的三个硬需求——多跳推理、图表检索、检索前授权——正是单独 RAG 缺的三块。

**「员工会把机密查出去吗？」** 这正是「检索前授权」在管的事：查询先过政策（DENY→ALLOW→fail closed），越权的内容根本不会进入员工的上下文；每笔特权检索留收据（[第 13 章](13-governance.md)）。

**「资料会上传到哪里？」** 脑数据是你机器上的文件（PGLite＋git repo），嵌入走本地 llama-server。会离开机器的只有模型推理本身（你设置的 LLM 端点）——清单见 [DEPLOYMENT.md §11.4](../../DEPLOYMENT.md)。
